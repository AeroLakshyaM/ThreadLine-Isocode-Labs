# Threadline Project Assessment Context

This note preserves the assessment brief supplied by the project owner for future Threadline work. It is project context, not a request to create or submit the assessment package in this turn.

## Project and deal context

- The assessment is a live-deal exercise for Isocode Labs, a custom website, web app, and AI automation studio.
- The product owner says this Threadline web app is the project that will be judged. Treat Threadline as the selected case for future assessment work unless the owner later names a different problem statement.
- Isocode's typical project budget is ₹5–10 lakh and typical duration is 4–8 weeks.
- The assessment window is 7 days from when the step opens. The exact opening/deadline date was not supplied.
- The submission is one ZIP (maximum 25 MB) containing three clearly named documents: the project PRD, the project timeline, and a draft agreement.

## Required contents

### PRD for the whole project

Cover the problem, goals, exclusions, users and journeys, prioritised first-release and later requirements, AI/automation behaviour and failure handling, design approach and key screens, data/integrations/business rules, risks, success measures, and open questions for the client.

### Project timeline

Set out phases, milestones, and deliverables week by week. Name responsibilities for both Isocode and the client. Include dependencies, buffers, and client approval points. Fit the stated 4–8 week and ₹5–10 lakh typical ranges unless the supplied problem statement justifies a clearly explained alternative.

### Draft agreement

Make it ready to send before closing the deal and mark it as a draft for legal review. Cover scope, exclusions, deliverables, timeline, price in rupees, payment milestones, change requests, client responsibilities, acceptance, ownership, confidentiality, data protection, post-launch support, termination, and signature blocks.

## Assessment rules

- Use only information in the selected problem statement. Label every assumption; do not invent client facts.
- Treat any engineering-oriented “CORE BUILD” paragraph as technical reference. Plan the whole project, not just the engineering build.
- Use AI to draft, critique, find gaps, and polish, while retaining human judgement over choices, numbers, and final commitments.
- Make trade-offs explicit and ensure budget, scope, and schedule agree with each other.
- Do not represent Isocode Labs or contact anyone outside this assessment task.
- The participant may resubmit until the deadline; only the latest version is reviewed.

## Scoring rubric

| Area | Weight |
| --- | ---: |
| Quality of work | 50% |
| Problem solving | 30% |
| Communication | 20% |

High-scoring work should be specific enough to build without avoidable clarification, have a credible schedule with client responsibilities and approval gates, include complete agreement mechanics, prioritise features, explain AI failure handling, and make careful, honest trade-offs.

## Threadline grounding for future assessment work

Threadline is a mobile-first garment-production order tracking PWA. Existing project documentation and source code are the grounding for product workflows and implementation status. Verify the current repository before drafting deliverables; do not turn synthetic preview records, unverified deployment claims, or unapproved factory thresholds/calendars into client facts. Distinguish implemented code from staging-tested and production-verified behaviour.

When asked to prepare the assessment submission, create the PRD, timeline, and agreement as separate polished files, verify that their scope, dates, cost, milestones, assumptions, and acceptance terms agree, then package them into one ZIP no larger than 25 MB. Do not send, upload, or represent the package externally unless explicitly asked.
